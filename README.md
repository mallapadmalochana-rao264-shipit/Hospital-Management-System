# MediCare Hospital Management System

Flask web application for hospital administration. It uses **SQLite** for relational hospital operations and **MongoDB Atlas** for flexible clinical documents.

## Database design

### SQLite (relational)
- `admin`: administrator login and password hash.
- `department`: hospital departments.
- `doctor`: doctors; each doctor belongs to one department.
- `patient`: patient demographic/contact details.
- `appointment`: appointment references one patient and one doctor.
- `bill`: patient billing, optionally linked to an appointment.

Relationships:
- `department 1 ── many doctor`
- `patient 1 ── many appointment`
- `doctor 1 ── many appointment`
- `patient 1 ── many bill`
- `appointment 1 ── zero/many bill` (bill appointment link is optional)

Schema and indexes are in `schema.sql` and are initialized automatically by `db.py`.

### MongoDB (document collections)
- `medical_records`: `patient_id`, `doctor_id`, `visit_date`, `diagnosis`, `symptoms[]`, embedded `vitals{bp,temp,pulse}`, `notes`.
- `prescriptions`: `patient_id`, `doctor_id`, `date`, embedded `medicines[{name,dosage,duration}]`, `advice`.
- `lab_reports`: `patient_id`, `doctor_id`, `date`, `test_name`, `status`, embedded `results[{parameter,value,unit,range}]`, `remarks`.

MongoDB `patient_id` and `doctor_id` are logical references to SQLite IDs; MongoDB cannot enforce cross-database foreign keys. The application performs basic cross-database cleanup/checks. `mongo_schema.js` documents the collection validators and indexes.

## Run locally in VS Code

1. Install Python 3.11+ and VS Code. Open this folder in VS Code.
2. Create and activate a virtual environment:
   - Windows PowerShell: `py -m venv .venv` then `.venv\\Scripts\\Activate.ps1`
   - macOS/Linux: `python3 -m venv .venv` then `source .venv/bin/activate`
3. Install dependencies: `pip install -r requirements.txt`
4. Copy `.env.example` to `.env` and set a strong `SECRET_KEY`, `ADMIN_PASSWORD`, and MongoDB Atlas `MONGO_URI`.
5. Load environment variables. Easiest option: use the VS Code Python terminal and set them in the terminal, or install `python-dotenv` and add `load_dotenv()` at the top of `app.py`. The app reads environment variables directly.
6. Start: `python app.py`
7. Open `http://127.0.0.1:5000`.

Default demo login if you have not set `ADMIN_USERNAME` / `ADMIN_PASSWORD`: `admin` / `admin123`. Change these before exposing the app publicly. The admin row is created only when the SQLite database is first initialized; changing the environment password later does not update an existing admin row.

## Deploy to Render

**Important:** the supplied application uses SQLite. Render's local filesystem is ephemeral unless a persistent disk is attached. The included `render.yaml` mounts a 1 GB disk at `/var/data` and stores the database at `/var/data/hospital.db`. Render persistent disks require a paid web service. The Blueprint therefore sets `plan: starter`; review Render's current pricing before creating it. If you remove the disk and use a free instance, SQLite data can be lost on redeploy/restart. For a fully free or horizontally scaled production deployment, migrate SQLite to managed PostgreSQL instead.

1. Push this folder to a GitHub repository. Do not commit `.env`, database files, or real patient data.
2. Create a MongoDB Atlas cluster, create a database user, allow network access for Render (Atlas network access settings), and copy the application connection string.
3. In Render, choose **New → Blueprint** and connect the GitHub repository containing `render.yaml`.
4. In the Render service environment, set `MONGO_URI` to the Atlas connection string and set a strong `ADMIN_PASSWORD`. Keep `SECRET_KEY` generated by Render. Confirm the disk is attached at `/var/data`.
5. Deploy. Render builds with `pip install -r requirements.txt` and starts Gunicorn.
6. Open the generated `onrender.com` URL and sign in using `ADMIN_USERNAME` / `ADMIN_PASSWORD`.

If you deploy without MongoDB Atlas, the app falls back to `mongomock` for a temporary demo. That data is in memory and disappears when the process restarts; do not use that mode for real records.

## Security / production notes

This is a student project starter, not a certified clinical system. Before using real patient information, add role-based access, CSRF protection, audit logging, encrypted backups, stricter validation, HTTPS-only cookies, privacy controls, and a tested recovery plan. Do not upload real patient records to a public demo.
